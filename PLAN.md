## Core research questions

1. What are the most frequent ordered **two-, three-, and four-command** family/shape sequences? How often do they occur, across how many distinct sessions, and in what kinds of workflows (read/search, Git, build/test/lint, deployment)?
2. For every **repeated normalized ordered sequence** (length 2, 3, or 4), how many occurrences were **explicitly batched**, **unbatched across distinct calls**, **mixed across a batch boundary**, or **unclassifiable**? Group the same sequence under one canonical key regardless of execution form, then show separate counts and session support for each form. Preserve command order and identify requested versus confirmed-executed subcommands; measure batch success/failure, early termination, missing output and dry-run cases.
3. Among direct calls, how often are commands adjacent at the **observable assistant/model response boundary**, rather than merely adjacent after filtering out all non-shell events? A single response may contain several tool calls; a proxy/API model request may be hidden or split in the trace. Distinguish: (a) same outer tool request / known multi-command call; (b) separate calls with no intervening model decision; (c) separate calls following tool output and a fresh assistant action; (d) pairs separated by code edits, reasoning, user turns, other tools or session discontinuity; (e) unknown boundaries. A transcript chronology is not a ground-truth API request log.
4. Which sequences appear **potentially batchable** according to conservative static criteria (e.g. format → test → lint, independent checks known in advance), and which are obviously decision-dependent (search → inspect, test failure → fix, output-dependent commands)? Count such candidates as **upper bounds**, not actual missed batching opportunities.
5. What is the distribution of inter-call elapsed time, intervening model/tool events, failure status, and observed output size? Does a pattern repeat in several independent sessions or only one long run? Where are `delayed-seq` wrappers already reducing tool calls?
6. Which **repeated sequences occur both batched and unbatched**, in which sessions, and with what different observable failure/decision boundaries? Report cross-mode overlap explicitly; do not interpret a batched occurrence as proof that every unbatched occurrence could be safely batched.
7. Would a small change to the existing batching instruction or a future workflow recommendation cover high-value patterns? Do not revise instructions based on raw frequencies alone.

## Proposed data model and extraction

Add privacy-safe chronological event records **during JSONL streaming**, rather than reconstructing interstitial decisions after discarding all but shell invocations. Proposed `TimelineEvent` fields: session identity (in memory only), source file identity/position (in memory only), monotonically increasing record index, timestamp or missing-timestamp flag, event kind (`user_turn`, `assistant_decision_or_message`, `shell_call`, `shell_output`, `non_shell_call`, `non_shell_output`, `edit`, `other`, `unknown`), correlated call IDs where present, tool type, and optional linked `ShellInvocation`. Record *event kind and correlation only*, not private prompt or message content. Identify observed `response_item`, `event_msg` and turn-context shapes from a bounded, redacted local structural sample; explicitly document supported envelopes and unknowns. Preserve duplicate-event handling and call-ID linkage.

**Canonical grouping (required):** Build an ordered tuple of privacy-safe command families or normalized shapes. Sequence identity must **not contain packaging or model-boundary fields**: the identical tuple must aggregate into the same report row whether observed in `delayed-seq`, unbatched tool calls from one observable model response, or separate responses. Each occurrence retains its packaging classification, confidence and boundaries, so the row shows totals **plus exact counts and distinct-session counts by category**. A logical model response is established only by verifiable rollout event structure/response IDs; if explicit boundaries do not exist, use `same_response_inferred`/`unknown`, never assert same API request from timestamp proximity. Disallow merging different model turns because two calls happened within a small time delta. A command sequence spanning a `delayed-seq` boundary must be identified as `mixed`, not silently attributed to either category. For cross-category comparisons report matched n-grams and overlap prevalence; dedupe nested overlapping windows only for a separately labeled non-overlapping occurrence metric, while regular n-gram frequency remains overlapping by definition. Expose every denominator.

**Ordering and boundaries**:
- Primary order is physical JSONL record order **within each session/rollout**, not timestamp-only sort. Stable per-file ordering and a deterministic merge policy are mandatory. If session ID is reused across files or histories overlap, never silently connect them; detect duplicates/overlap and mark unknown boundaries. `serial` should not imply a model turn boundary.
- Preserve explicit outer custom `exec` bundles and their inner tool-call order; multiple embedded calls may share one result key. One outer call may contain multiple operations but this does **not** imply sequential execution, especially with `Promise.all` / parallel constructs. Distinguish **same observable response** from **same custom-tool bundle**; mark parallel, unordered or ambiguous bundles as unknown, not ordered sequential occurrences. Detect whether multiple tool calls were issued within one model response using supported response boundaries, not only a shared `call_id` or time.
- For each ordered direct-call edge, record gap in event count, intervening event classes, observed tool-result presence, known user/new-turn markers, elapsed-time bucket (if credible), and evidence class. No `no_intervening_model_decision` claim merely because `event_msg` did not record reasoning: provider traces may omit internal reasoning and API boundaries. Use `not_observed` rather than `absent` where necessary.
- For nested `delayed-seq` shell wrappers, report explicit requested command sequence and per-subcommand completion only when wrapper output confirms it. Preserve failed/unknown remainder; do not treat shell operators such as `&&` within one command string as `delayed-seq` subcommand boundaries.
- Distinguish command **family** sequences (e.g. `cargo fmt → cargo test`) from normalized **shape** sequences (e.g. `cargo fmt --all --check → cargo test --lib`); use conservative shell analysis confidence and report the excluded/opaque share. Never output raw arguments, filenames, repository names, environment values, source text or session IDs.
- **Canonical repeat grouping:** Define a sequence key as `(granularity: family|shape, ordered tuple of 2–4 normalized command identities, parser-confidence class)`; keep batch mode **out of the key**, so the identical ordered sequence aggregates together before mode stratification. Annotate each observed occurrence with `explicit_batch`, `separate_direct_calls`, `mixed_batch_and_direct`, or `unknown`. A shell pipeline or `&&` expression is a **single shell invocation**, not an explicit `delayed-seq` sequence; if syntactic segments are shown, publish in a separate `syntax_only` table, never merge with proven requested batch subcommands.
- **Repeated sequence counting:** For each key count total occurrences, distinct sessions, sessions per mode, counts per mode, confirmed-executed vs requested-only batch occurrences, matched-result coverage, error/unknown boundaries, and observed output bytes only where attribution is exclusive. Preserve order, allow overlapping n-grams by design (e.g. A→B→C yields A→B and B→C) but label these as **overlapping windows**, not independent samples. Count one occurrence once within each length and scope, prevent duplicate replayed records from inflating counts, and avoid manufacturing a cross-boundary occurrence when a batch ends or a user turn intervenes. Provide both event-weighted counts and session-weighted support to prevent one long session dominating.
- **Co-occurrence modes:** An explicit batch is a contiguous known list of requested subcommands in **one actual `delayed-seq`/native-batch invocation**. A separate-direct sequence is made of successive direct shell invocations with evidence/boundary annotations; it is not automatically safe to batch. A mixed sequence can contain steps in one explicit batch and adjacent steps outside it, but only if observed chronological proximity and boundaries are available; otherwise classify as unknown and do not join. Keep explicit-batch, direct, and mixed denominators and eligible-window counts, so rates are interpretable.

## Aggregation and reporting behavior

Extend `build_report` with a versioned `sequence_analysis` section, or a clearly documented separate output with a schema version; preserve the established schema-v2 fields and their meanings unless explicitly versioned. Add `command_sequence_report.md` and `command_sequence_report.json` to the **user-selected local output directory** through `write_reports` and CLI summary. Ensure existing outputs are not inadvertently overwritten in a way that changes previously published semantics. New files must have the same private permissions and redaction guarantees as current outputs.

Report at least:

- Coverage: sessions/files/records, timeline events classified, calls/outputs matched, missing/unknown boundaries, requested vs confirmed-executed batch subcommands, number of sequences by evidence class.
- **Primary repeated-sequence ranking:** Top 20 ordered pairs, top 15 triples, top 10 four-command sequences, keyed by the **same normalized ordered sequence regardless of batch mode**. For each, include `total`, `explicit_batch`, `separate_direct_calls`, `mixed`, `unknown`, `distinct_sessions`, distinct sessions per mode, evidence/confidence, requested/confirmed-executed counts, observed status and eligible-window denominators. Highlight cross-mode repeats with both `explicit_batch > 0` and `separate_direct_calls > 0`.
- Provide separate detailed tables for explicit `delayed-seq` sequences and cross-invocation/direct sequences **alongside**, not instead of, the unified grouping; never silently blend execution claims or denominators. Add a `batched_fraction` defined only over explicitly classified eligible occurrences, exclude unknowns, display the denominator, and do not present it as the fraction safely batchable.
- A cross-mode comparison table for the same repeated sequence: batched/unbatched/mixed occurrence counts, distinct-session support, within-session mode overlap (without revealing session identities), output/result coverage, observed failure rates with denominators, and a conservative rationale for whether an unbatched occurrence was decision-dependent. Rank these especially when the sequence is frequent in both modes.
- A normalized pair/triple transition analysis: `count(A → B)`, support across sessions, conditional follow rate `P(B next | A)` with denominators and no causal claim. Include high-frequency patterns and low-frequency high-output patterns. Never infer per-subcommand output from a combined wrapper result.
- Intervening-events histogram for direct edges, with classes `none_observed`, `tool_output_only`, `assistant_decision_observed`, `edit_or_other_tool`, `user_turn_or_session_boundary`, `unknown`. These labels characterize observed traces, not actual hidden model decision boundaries.
- Conservative *batching-candidate* list with recommended category (`plausible_static_sequence`, `decision_dependent`, `unsafe_or_ambiguous`, `already_batched`), counts, completion/failure data, status of required intermediate model decisions, and examples as sanitized command shapes only. Rank by frequency and existing output/call context, not hypothetical model-call savings alone.
- For each canonical sequence calculate `batch_count / eligible_observed_count` and `unbatched_same_response_count / eligible_observed_count` **only** with a defined eligibility denominator and proven same-response boundary; otherwise return `null` with coverage reasons. Rank sequences **repeated across both batched and unbatched same-response contexts** separately: these are the most actionable consistency examples for refining AGENTS.md selection guidance. Compare explicit-batch and direct distributions, report unknown/mixed cases and missing data. A same-response tool-call series is evidence of common planning but **not proof** that batching would preserve tool output/intermediate decisions, concurrency or execution correctness.
- No automatic execution, batching, tool rewriting, proxy changes, model invocation or online service. Avoid treating elapsed time alone as evidence that no decision happened. Weighting by uncached input is speculative without request-level token counters; `U + 0.1*C + 5*O` only when validated provider usage is available.

## Test strategy and validation

Use deterministic synthetic JSONL fixtures and fake timestamps (no real sleeps or outside services). Test:

1. Same-session direct adjacent calls with intermediate assistant/tool-output records, non-shell tool/edit interruptions, user-turn boundaries and missing event types; verify classification and denominator reconciliation.
2. Direct sequences of length 2/3/4 and overlapping n-grams; multiple sessions and a single dominant session; repeated shapes and distinct-session counts. **Identical sequences observed once inside `delayed-seq` and repeatedly as unbatched calls in the same observable model response must merge into one canonical row** with separate packaging counters. Include identical sequence across *different* model responses, ambiguous model boundaries, mixed batched/unbatched boundaries and no false same-response attribution. The same A→B→C shape appears across explicit batches, independent direct calls, and mixed mode: assert **one canonical group** with correct per-mode counters and distinct session support; do not split its identity by mode or count duplicate replay events twice.
3. One explicit `delayed-seq` sequence with all successes, early failure, timeout, cancellation, dry-run and missing wrapper output; requested versus executed counts and no output double counting. Test batch boundary followed by direct call and user turn, cross-batch adjacency, unknown ordering, malformed wrapper, and denominator-aware batched fraction. A sequence only **requested** in a batch must not be represented as fully executed if the batch stopped early.
4. Native `delayed_seq`, ordinary `delayed-seq -- ...`, proxy-marker batch and ambiguous custom `exec` multi-tool bundles including concurrency/parallel constructs; distinguish tools issued by one model response versus tools issued across two model responses even if timestamps match. Verify reported category totals sum to canonical sequence occurrence totals without double counting nested batch events.
5. Compound shell scripts (`&&`, pipelines, variables, heredocs) are not misidentified as deterministic multi-step batch invocations. Preserve `ShellAnalysis` partial/opaque handling.
6. Missing/identical timestamps, physical record order, duplicate/overlapping rollout files, reused call IDs, duplicate request/result events, orphan outputs and actively appended partial JSONL lines.
7. Report schema compatibility, deterministic sorting and byte-identical reports, privacy/secret non-leakage across Markdown, JSON, CLI stderr and error cases, size/line/record bounds, symlink handling.
8. Regression: legacy command-frequency, opaque-reason and adapter-priority totals unchanged for identical input when new sequence reporting is added; change only with explicit justified schema migration.
