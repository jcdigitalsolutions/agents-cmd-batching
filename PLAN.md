- Rust: `cargo build`, `cargo check`, `cargo clippy`, `cargo test`, `cargo nextest run` if observed, direct `rustc`, optionally `rustfmt`/`cargo fmt` as **format**, not compile. Distinguish `--release`, workspace, targets, features, and `--no-run` only as privacy-safe shape flags; no raw paths.
- Go: `go build`, `go test`, `go vet`, `go fmt`/`gofmt`, and `go generate` only if observed (side-effecting; no compression equivalence assumed).

- Classify `compile/build`, `type/check`, `lint`, `test`, `format`, `package-script-unknown`, `unknown`. Keep exact executable/subcommand variants and direct vs wrapped/batched dimensions. Preserve syntax-only counts in a separate section from confirmed executions.

For each normalized command shape and broader family, compute: number of calls; sessions/files; **direct / explicit shell batch / native batch / proxy batch / mixed or unknown**; syntactic-only compound appearances; matched/unmatched/ambiguous/composite results; **confirmed started, completed-success, completed-failure, cancelled, timed-out, unknown**; original output bytes and lines (total, mean, median, p90, p95, max), zero-output rate, stderr/warning/truncation indicators, and already-quiet commands. ## Phase 3 — offline compression experiments

### Verified statuses and guardrails

**Do not collapse output based on words like `passed` or `compiled successfully` alone.** Require an authoritative recorded zero exit status for the complete process (structured `exit_code` or unambiguously parsed tool exit metadata), untruncated/unambiguous output, known command family with a reviewed formatter, and no warnings/errors/notes of concern, skipped/ignored/xfail tests, deprecations, suspicious nonstandard stdout, or unexpected interactive prompts. Test results may need minimal suite counts or ignored-test information even when exit 0; a `Success!` outcome is a separate *aggressive research candidate*, not automatically safe for production. Record `success_verified`, `success_text_inferred`, `failed_verified`, `failure_text_inferred`, `timeout`, `cancelled`, `unknown` separately.

**Candidate A: `Success!\n`**: simulate exactly this single-line output for clean, verified successful compilations / build / check / lint / tests **only after per-tool fixtures demonstrate no hidden actionable information**. Never replace actual process status or suppress legitimate security/warning diagnostics. Do not label an unverified result `Success!`. Compare this aggressive variant to a conservative compact summary retaining command identity and test counts. Zero-output clean success is passthrough (a replacement would be larger). Account for terminal/wrapper envelope and any needed metadata, not merely stdout savings.

**Candidate B: terse failure**: build per-ecosystem *output-only* parsers, initially limited to Rust Cargo/rustc, Go `go build`/`go test`, Node/TS build and test runners, and Python validators where enough matched observations exist. Preserve decisive error code, failing target/package/test, exact relevant filename/line/column if needed at runtime, primary diagnostic text, all unique failures (or explicit bounded truncation with durable recovery), warnings associated with failure, stderr and final status. Preserve original command output for unknown/unsupported formats, compiler ICEs, crashes, panics, race reports, linker errors, OOMs, signal exits, timeout/cancellation, binary output, multi-error spillover, and output truncation unless a proven lossless/safe parser exists. Report omitted detail and risks, never quietly turn a failure into a success.

**Research privacy:** It is permitted to temporarily process raw local tool text in memory to simulate transforms. **Never serialize actual commands, paths, compiler diagnostics, snippets, secrets, file contents or invocation IDs** to reports or telemetry. For published aggregates, use sanitized family labels / structural categories only; optional manual local review requires explicit consent. Code/tests may use synthetic fixture diagnostics with artificial paths.

**Comparison:** baseline no compression; existing conservative cleaner; aggressive `Success!`; and terse-failure with full original fallback. Measure per command and per output type: eligible/attempted/transformed/skipped counts, bytes original vs transformed, delta and percentage; impact by session/file, direct vs batch; p50/p90/p95 savings; reconstructed observation-token ranges using established byte heuristic; token overhead of any prompt/tool-wrapper envelope. Display **total observable opportunity**, not summed overlapping windows. Avoid interpreting bytes as proven cache misses or dollars saved. A follow-up controlled A/B coding-agent benchmark (not in scope) must assess whether reduced context triggers extra reads/retries or harms debugging; include planned task-level metrics and exit-code parity for that future work.

**Significant savings criterion:** report absolute and relative savings, not a subjective label. Supply thresholds as configurable reporting parameters (proposed defaults: >= 20% of bytes *within the targeted family* and >= 100KiB observed bytes saved across the full cohort); also report the fraction of **all matched shell-output bytes** affected. If no family meets both, conclude no significant demonstrated savings. These thresholds are evaluation gates, not an incentive to omit diagnostics.
